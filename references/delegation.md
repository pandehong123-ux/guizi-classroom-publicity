# 主控的实际调度方法

使用当前环境真实提供的子智能体 API，不使用未经验证的配置格式。Skill 本身提供可复制的角色任务规范，并在启动时交给真实子智能体；它不是三个永远运行的后台服务。

当前 Codex Desktop 会话可用 `collaboration.spawn_agent`、`send_message`、`followup_task`、`list_agents`、`wait_agent`。使用工具的实际 schema；这些工具必须直接调用，不从 `functions.exec` 内调用。当前会话可容纳主控加三个角色。

启动三个角色时：

1. 主控读取对应 `roles/*.md`，把角色全文和下面任务上下文传给子智能体，使用隔离上下文 `fork_turns: "none"`；不硬编码模型。名称如 `publicity_creator`、`publicity_visual`、`publicity_reviewer`。
2. 任务上下文包含：Skill绝对路径、源项目绝对路径、活动说明/用户本次要求、工作目录、当前阶段、已确认版本（制作阶段才有）、必读参考、可写文件与禁止写范围。
3. 文案先工作；视觉等文案方案文件存在再工作；审核等两者提交再工作。依赖工作顺序执行，独立取证可以并行。无需让用户安排角色顺序。
4. 用 `followup_task` 请求已有角色处理下一阶段或返修，避免新建同角色。工具不可复用或角色已不可用时，明确上下文和阶段，重新启动该角色。
5. 主控检查实际文件，不能只凭角色“完成”消息判断成功。保存每轮 `方案审核.md` 或 `成稿审核.md` 和修正情况。

可直接构造的任务消息：

```text
你是本任务的视觉策划智能体。以下为完整角色规范：
（主控在这里附 roles/visual.md 的全文）

Skill目录：当前实际绝对路径。
资料目录：本次实际绝对路径。
工作目录：本次实际绝对路径。
阶段：方案。用户尚未确认，不得制作最终Markdown或完整提示词。
用户本次要求：本次原话和活动说明。
读取：文案方案.md、内容分析.md、原始HTML及关联实现、Skill参考规范。
允许写：视觉方案.md、图片清单.json。
提交后报告文件路径、各小节图数和无法核实的内容。
```

这是消息格式说明，运行时要填真实信息，不把上面的说明文字原样当任务资料。

未来环境若提供其他 `spawn_agent` 接口，用真实可用接口发送同样角色规范。只有支持实际 Agent类型注册的环境才考虑原生类型配置；`agents/openai.yaml` 不注册三个角色。不要使用 `.cursor/agents` 宣称已经部署 Codex 原生智能体。

没有任何可用子智能体调度工具时，告知用户缺少实际并行/独立角色调用能力，保留方案文件并说明需要支持子智能体的环境。除非用户同意替代方式，不默默改为主控扮演三个角色并称其已经运行。
